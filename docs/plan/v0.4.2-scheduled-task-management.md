## 2. Context and Product Decisions

v0.4.1 delivered the shared schedule list, configuration detail, and run history for ordinary users and administrators. Runtime v0.6.5 now completes the native management API and changes ETF Grid execution into two independent Workflows:

- `etf_grid_data_sync` is system-only and has exactly one code-registered, unowned schedule.
- `etf_grid_recompute` runs for the authenticated schedule owner and has no automatically created personal schedules.
- Sync and recompute have no ordering guarantee or cross-schedule dependency. The Client must not imply that creating or running one causes the other.

This milestone remains core platform UI rather than an ETF Grid extension. ETF Grid is the first and only ordinary-user target exposed by this version, but schedule state, execution records, and management calls continue to use the native `/schedules` contract.

Confirmed Client behavior:

1. **Full management includes state and execution actions.** In addition to CRUD, the page exposes enable, disable, and manual trigger because they are part of the Runtime v0.6.5 user-managed schedule lifecycle.
2. **Ordinary users manage permitted personal Workflow schedules only.** Create and edit select from the scope-filtered native catalog returned by `GET /workflows`; this version currently exposes only the recompute Workflow to ordinary users. The form derives `POST /workflows/{workflow_id}/runs` and does not accept an arbitrary endpoint, HTTP method, owner, Workflow id, or system-sync target from an ordinary user.
3. **Administrators receive the full Workflow catalog.** Admin mode can select system and non-system Workflows and manage public/system and other users' visible schedules. Arbitrary local Runtime paths remain available only through native break-glass API use, not this form. Catalog visibility does not grant execution; Runtime remains the authorization boundary and rechecks target run permission.
4. **No ownership override exists.** Requests never contain `user_id`, an owner query parameter, or an “all users” option. A schedule created through REST belongs to the authenticated creator, including when the creator is an administrator; the UI does not claim to create unowned system schedules.
5. **Code-managed system schedules remain Runtime-owned configuration.** Admin mode may use the native edit/state/delete operations on them, but the UI warns that startup reconciliation can restore or overwrite the code-registered `etf_grid_daily_sync`. This milestone does not add a Client-side lock or a second system-schedule registration path.
6. **Server responses are authoritative.** No optimistic create, update, state, trigger, or delete rendering is used. Existing read behavior, role separation, and chat preservation remain unchanged.

## 3. API and Presentation Contract

### 3.1 Runtime endpoints and typed wrappers

Extend `src/scheduled-tasks-api.ts` on top of `runtimeRequest`; do not add a feature-specific HTTP or authentication layer.

| Method | Path | Success response | Client use |
|--------|------|------------------|------------|
| GET | `/workflows` | 200 `WorkflowSummary[]` | Native scope-filtered Workflow catalog for create/edit |
| POST | `/schedules` | 201 `Schedule` | Create an enabled personal schedule |
| GET | `/schedules` | 200 `{data, meta}` | Existing paginated visible-schedule list |
| GET | `/schedules/{schedule_id}` | 200 `Schedule` | Existing fresh detail |
| PATCH | `/schedules/{schedule_id}` | 200 `Schedule` | Update editable configuration/target fields |
| DELETE | `/schedules/{schedule_id}` | 204 empty | Delete a visible schedule |
| POST | `/schedules/{schedule_id}/enable` | 200 `ScheduleState` | Enable and recompute next run |
| POST | `/schedules/{schedule_id}/disable` | 200 `ScheduleState` | Disable without deleting |
| POST | `/schedules/{schedule_id}/trigger` | 200 `ScheduleRun` | Execute an enabled schedule and await its recorded result |
| GET | `/schedules/{schedule_id}/runs` | 200 `{data, meta}` | Existing run history |
| GET | `/schedules/{schedule_id}/runs/{run_id}` | 200 `ScheduleRun` | Existing expanded execution detail |

Add strict `WorkflowSummary`, `ScheduleCreateInput`, `ScheduleUpdateInput`, and `ScheduleState` types. The form derives a `POST /workflows/{workflow_id}/runs` target from each Workflow summary with an id. Reuse the existing `Schedule`, `ScheduleRun`, and pagination types. Encode every path id. Wrappers may accept `AbortSignal` so obsolete UI completions can be ignored, but aborting a browser mutation must never be described as cancelling a server-side write or execution.

Create fields and native defaults/constraints:

| Field | Rule |
|-------|------|
| `name` | Required; maximum 255; starts alphanumeric and otherwise contains only alphanumerics, spaces, `.`, `_`, `-`; unique within the caller's schedule scope |
| `cron_expr` | Required; maximum 128; Runtime validates the cron expression |
| `endpoint` | Required Runtime-local path supplied by the selected Workflow target; maximum 512 |
| `method` | Supplied by the selected Workflow target; currently `POST` for every catalog entry |
| `description` | Optional/null; maximum 1024 |
| `payload` | Optional/null JSON object; no array or scalar payload |
| `timezone` | Defaults to `UTC`; maximum 64; Runtime validates the timezone |
| `timeout_seconds` | Integer 1–86400; default 3600 |
| `max_retries` | Integer 0–10; default 0 |
| `retry_delay_seconds` | Integer 1–3600; default 60 |

`ScheduleUpdateInput` contains only optional editable fields. Omitted fields remain unchanged; `description` and `payload` may be explicitly null, while required configuration fields cannot be set to null. Do not send `enabled`, `next_run_at`, ownership, provenance, timestamps, or run fields through PATCH. State changes use their dedicated routes.

For the ordinary-user Workflow target, payload follows the native Workflow run input and defaults to:

```json
{"message": "Run scheduled ETF Grid recompute"}
```

The Workflow obtains its owner from the verified schedule owner. A payload-supplied user id is neither offered nor used by the Client.

Native status behavior that the UI must preserve:

- Create always returns `enabled: true` with a computed `next_run_at`; there is no create-time enabled field.
- Enable/disable returns only `id`, `name`, `enabled`, `next_run_at`, and `updated_at`. Merge that state into the open detail or refetch the full schedule rather than treating it as a full `Schedule`.
- Changing cron/timezone on an enabled schedule recomputes `next_run_at`; changing a disabled schedule does not arm it.
- Manual trigger is disabled for a disabled schedule. Runtime returns 409 if stale UI attempts it.
- Manual trigger waits for execution and returns a `ScheduleRun`. HTTP 200 means the trigger request completed, **not** that the task succeeded; render the returned run's `status`, `status_code`, and `error` and refresh history.
- Native 401/403/404/409/422/503 responses retain their meanings. In particular, 409 covers duplicate names, disabled trigger, and invalid target state; 422 covers field, cron, timezone, and JSON validation; 503 can mean scheduler unavailable.

### 3.2 Target and role policy in the form

| Capability | Ordinary user | Administrator |
|------------|---------------|---------------|
| Create target | Select from the scope-filtered catalog; recompute is preferred as the default | Select from the full catalog |
| Edit target | Select from the scope-filtered catalog | Select from the full catalog; Runtime rechecks target permission when method/endpoint changes |
| Visible schedules | Own personal schedules only | Public/system and all users' personal schedules |
| Owner assignment | Never exposed | Never exposed |
| State/delete/trigger | Own visible schedules | Every visible schedule, subject to native response |
| System-sync Workflow | Not offered by the current ordinary-role catalog | Offered through the catalog |

The form uses `mode` only to choose presentation. Target visibility comes from Runtime's native Workflow-scope filtering; the Client does not infer fine-grained permission from JWT claims, infer a system/personal flag absent from the native response, or hide Runtime authorization failures. A caller lacking `workflows:read`, `schedules:write`, `schedules:delete`, or Workflow run permission receives an understandable 403 from the real request.

### 3.3 Create and edit dialog

Add one shared schedule-form dialog using the vendored shadcn `Dialog`, `Input`, `Select`, `Button`, and existing layout primitives. Do not add a form library, cron parser, timezone package, toast dependency, or new UI component library.

- The page header replaces the Read-only badge with **New schedule**; Refresh remains.
- Create starts with an empty name/cron/description and the native numeric/timezone defaults above. After the target catalog loads, recompute is preferred as the default target, with the first catalog entry as fallback; the native Workflow `message` payload remains the default.
- Edit opens from a fully loaded schedule detail and is prefilled from that fresh response, not stale list data. An existing target missing from the catalog remains available as a clearly labelled current-target option so unrelated fields can still be saved.
- Fields: name, description, cron expression, timezone, a Workflow target selector, JSON payload, timeout, maximum retries, and retry delay. The selected target supplies method/endpoint. Current enabled state and next run remain detail content, not form inputs.
- Keep cron as a raw text value with short format guidance. Select timezone from common IANA options, retaining an existing schedule's configured value as an additional option when necessary. Runtime validation remains authoritative; no cron humanization, next-run preview, or timezone dependency is introduced.
- Perform lightweight local checks for required values, numeric ranges, and payload syntax/object shape. Do not duplicate Runtime's complete cron, timezone, target, or uniqueness rules.
- Prevent accidental dialog dismissal and duplicate submission while saving. Keep entered values after a failed request.
- Display field-mappable 422 messages near the relevant control when possible and all remaining Runtime messages in a dialog-level error alert. Never silently discard `detail[]` entries.
- On create, close the dialog, refresh the list, and open the returned schedule's detail so the result is visible regardless of list ordering. On edit, apply the returned full `Schedule` to the open detail and refresh the list; preserve run-history context unless target/schedule identity changed.
- Show one inline success/status notice in the page or detail surface; no global notification system is added.

### 3.4 Detail actions and mutation lifecycle

Place **Edit**, **Enable/Disable**, **Run now**, and **Delete** in the schedule detail Sheet. The list remains free of per-row mutation buttons and extra run fan-out.

1. **Enable/Disable**
   - Show the action matching the current server state, with a pending label and spinner.
   - Merge the returned `ScheduleState`, refresh list state, and ensure the open full detail remains coherent.
   - Show `next_run_at` returned by enable. Disable preserves configuration and history.
   - Do not automatically retry a failed state mutation.

2. **Run now**
   - Available only for an enabled schedule; disabled state includes an explanation.
   - Use a confirmation dialog because execution can cause immediate side effects, especially for system Workflow targets. The confirmation explains that the request waits for a run result and leaving the page does not cancel execution.
   - While running, prevent duplicate trigger and conflicting edit/state/delete actions for that schedule. Keep the existing detail readable and show a persistent pending state.
   - On completion, display the returned run status rather than a blanket success message, move run history to page 1, and refresh schedule detail/list plus run history. Failed runs render their returned error without being thrown away as a transport failure.
   - Closing the Sheet or aborting UI work does not claim to stop the Workflow. A later open/refresh must be able to observe the persisted run.

3. **Delete**
   - Use a confirmation dialog naming the schedule and stating that deletion cannot be undone. Do not claim a particular run-history cascade behavior beyond the native API contract.
   - On 204, close the Sheet and confirmation, clear obsolete selection/run state, and refresh the list. If the deleted row was the last item on a page greater than 1, move to the previous page before reloading.
   - A 404 means the schedule is already missing or inaccessible: close invalid detail state and refresh rather than retrying the delete automatically.

All mutations for one schedule share explicit pending/action state so double-clicks and overlapping operations cannot issue conflicting writes. Create/edit/delete dialogs do not silently dismiss during submission. Async completions after a newer selection, role change, or unmount must not overwrite current UI. Mutation requests are never automatically retried.

### 3.5 Errors, refresh, and existing read behavior

- Preserve independent list, schedule-detail, run-list, and run-detail loading/error states from v0.4.1.
- Keep mutation errors in the active dialog or Sheet so valid configuration/history remains visible. Use specific access-denied, missing/inaccessible, conflict, validation, scheduler-unavailable, and generic request copy.
- A 401 follows shared re-authentication. A 403 is not automatically retried. A 404 closes stale detail when appropriate and offers/list-refreshes. A 409 or 422 keeps editable form state. A 503 is manually retryable.
- Refresh after mutations uses actual responses and GETs, not fabricated list rows. Manual Refresh retains the current filter/page/selection behavior; there is still no polling or live-update stream.
- Filter and page transitions close stale detail as before. Deleting and triggering reset only the child state required by their result; unrelated chat and admin overview state are untouched.
- Remove the read-only header badge, read-only footer note, and read-only descriptions. Replace them with role-appropriate management descriptions and English `common` keys; do not leave copy claiming writes are unavailable.

### 3.6 Navigation and role boundaries

No new navigation entry or router is introduced. Both roles continue to use `ScheduledTasksPage` through their existing local view state.

- Ordinary Chat stays mounted but hidden while Scheduled tasks is active; returning to Chat preserves the conversation.
- Admin mode continues to mount no chat, CopilotKit provider, thread agent, extension views, or `/agui` requests.
- Scheduled-task REST writes use the same Bearer token and Runtime base URL as existing reads. No tokens, role state, schedule drafts, schedule responses, or ownership data are persisted to `localStorage`.

## 4. Scope

### 4.1 In Scope

1. Typed native Workflow discovery and Agno-native create, update, delete, enable, disable, and trigger wrappers, including create/update/state contracts and existing read compatibility.
2. Shared create/edit dialog with a scope-filtered Workflow target selector supplied by the native Runtime catalog.
3. Detail-Sheet edit, state-change, confirmed manual-trigger, and confirmed delete actions with complete pending/success/failure behavior.
4. Correct list/detail/run-history refresh, pagination correction after delete, stale-response handling, and native error rendering for every mutation.
5. Removal of obsolete read-only copy and complete English `common` internationalization for new labels, guidance, confirmations, and statuses.
6. Documentation, version update, and real-Runtime two-role management walkthrough.

### 4.2 Out of Scope

- Runtime, Agno, Logto, Workflow implementation, scheduler, or authorization changes.
- A custom schedule API, Action registry, generic dispatcher, client-side owner selection, unowned schedule creation, or automatic personal-schedule migration.
- Manual endpoint/method entry, arbitrary target selection, natural-language schedule management, SchedulerTools, or chat/HITL integration.
- Cron parsing/humanization, next-run simulation, calendar/trading-day awareness, schedule dependencies, sync-before-recompute promises, and automatic catch-up chains.
- Notifications, proactive updates, auto-refresh, bulk operations, schedule search/owner filters, dashboards, run deletion/replay, or domain-specific run-result cards.
- Router/deep links, a state-management library, a new test framework, new runtime dependencies, and non-English locale additions.

## 5. Success Criteria

- [ ] An ordinary user can create an enabled personal schedule by selecting `etf_grid_recompute` from the native Runtime Workflow catalog; the request contains no owner override and the returned schedule appears in detail/list after refresh.
- [ ] The same user can edit target/configuration/payload, disable, re-enable, manually trigger, inspect the resulting run, and delete only their own schedules. Bob receives the native missing/inaccessible behavior for Alice's ids.
- [ ] Ordinary-user UI cannot submit an arbitrary extension endpoint or the system data-sync Workflow. Runtime 403 remains enforced even for a handcrafted request.
- [ ] An administrator can select any full-catalog target, including system-sync, and manage public/system and other users' visible schedules. Admin-created REST schedules are labelled with their actual returned owner, never as unowned system tasks.
- [ ] Target loading, empty, failure, and retry states are visible; create cannot submit without a selected target, and an existing off-catalog target is preserved when editing unrelated fields.
- [ ] Create/edit honor native field constraints, nullable description/payload, PATCH omission semantics, numeric ranges, and Workflow `message` payload shape; invalid cron/timezone/JSON and duplicate names produce visible 422/409 feedback without losing input.
- [ ] Enable/disable use their trimmed response correctly; enabled next-run timestamps and disabled states stay consistent between list and detail.
- [ ] Run now cannot be submitted for a disabled schedule or duplicated while pending. Its returned failed run is shown as a failed execution despite HTTP 200, and successful/failed attempts appear in refreshed run history with linked Workflow output when present.
- [ ] Delete requires confirmation, handles 204 and stale 404 correctly, closes obsolete detail, and repairs pagination when the final row on a later page is removed.
- [ ] 401, 403, 404, 409, 422, 503, network failure, slow trigger, dialog close, selection change, and unmount behavior follow Section 3 without optimistic or stale UI corruption and without automatic mutation retries.
- [ ] No UI or copy promises sync/recompute ordering, automatic personal schedules, unowned REST creation, or cancellation of server execution by closing the browser UI.
- [ ] Chat state survives ordinary-user view switches; admin mode continues to emit zero `/agui` requests. Existing filtering, read pagination, run expansion, and responsive behavior still work.
- [ ] All user-facing copy resolves through `common`; `npm run lint`, `npm run typecheck`, and `npm run build` pass.

## 8. Manual Verification (owner walkthrough)

Prerequisites:

1. Runtime v0.6.5 is running with real Logto JWTs, user isolation, the unowned `etf_grid_daily_sync`, and both extension Workflows. Ordinary role tokens include `schedules:read`, `schedules:write`, `schedules:delete`, `workflows:read`, and resource-level `workflows:etf_grid_recompute:run`, but no system-sync run permission.
2. Logto provides administrator, Alice, Bob, a read-only schedule caller without write/delete scopes, and a caller with schedule write but without recompute run permission for 403 checks.
3. Fixtures include Alice/Bob personal schedules, disabled schedules, successful and failed recompute runs, and enough rows for pagination. Do not use a destructive external endpoint for trigger tests.
4. Start this app with `npm run dev` on port 3000.

Walkthrough:

1. Sign in as Alice. Open create and confirm the scope-filtered `GET /workflows` response supplies only the recompute Workflow, whose derived run target becomes the default selection. Create a schedule, then edit target/configuration and Workflow message payload. Inspect requests: the selected target submits `POST /workflows/etf_grid_recompute/runs`; no `user_id` or owner query is sent; create returns enabled with next run.
2. Submit invalid required/numeric/JSON values and then Runtime-rejected cron/timezone and a duplicate name. Verify local or native messages are readable, all 422 `detail[]` messages remain available, and entered values survive. Confirm a disabled schedule stays disabled after editing cron/timezone until explicitly enabled.
3. Disable and enable Alice's schedule; verify badges, next run, and list/detail consistency. Attempt Run now while disabled and confirm it is unavailable. Enable it, trigger a real run, and observe pending behavior, returned run status, refreshed run history page 1, linked run/session ids, and structured output. Trigger a controlled failure and verify HTTP 200 with a failed `ScheduleRun` is presented as failure.
4. While a trigger is slow, attempt duplicate/conflicting actions and close/reopen the Sheet. Verify no duplicate request is issued, no UI claims server cancellation, and refreshed history eventually shows the persisted result. Block Runtime or force 503 and confirm manual retry behavior without automatic write retries.
5. Delete Alice's schedule from its confirmation dialog and verify 204, closed detail, refreshed list, and no stale run requests. Delete the only schedule on page 2 and verify recovery to page 1. Repeat a stale delete/detail case and verify 404 recovery.
6. Sign in as Bob. Confirm Alice's schedules are absent and direct cross-user read/write/state/trigger/delete ids produce native 404 handling. Confirm Runtime has not automatically created a personal schedule for Bob; create one explicitly and verify recompute affects Bob's owner context only.
7. Using a caller without `workflows:read`, verify target discovery shows a specific 403 with manual retry and create cannot submit. Using the read-only caller and then the caller lacking Workflow run permission, verify visible management requests produce specific 403 states without automatic retries. As Alice, also verify a handcrafted system-sync or arbitrary-extension target remains forbidden even though the UI never offers it.
8. Sign in as admin. Confirm the catalog contains system and non-system Workflows. Create and edit a disposable schedule targeting the system-sync Workflow; verify the selected method/path are submitted and target permission remains Runtime-enforced. Manage another user's schedule and inspect actual Owner labels. Confirm admin-created schedules carry the admin subject, not `user_id: null`.
9. On the code-managed `etf_grid_daily_sync`, verify the reconciliation warning and non-destructive edit/disable/enable behavior only if it can be restored safely. Do not delete the sole production fixture for this walkthrough. Confirm no UI promises sync-before-recompute ordering or creates personal recompute schedules automatically.
10. Exercise target-catalog empty/loading/failure/retry states and an existing off-catalog schedule target, then slow network, 401 re-authentication, 403, 404, 409, 422, 503, and Runtime-unreachable cases across dialogs and detail actions. Confirm valid read content is not erased by mutation errors and stale completions cannot affect a newly selected schedule.
11. Switch between Chat and Scheduled tasks after edits and triggers; verify the conversation survives. In admin mode, inspect DevTools Network and confirm zero `/agui` requests. Repeat dialogs, Sheet, action controls, and history at a narrow viewport and with the sidebar collapsed.
12. Run `npm run lint`, `npm run typecheck`, and `npm run build`.
