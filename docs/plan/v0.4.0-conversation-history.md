## 2. Context

Today the client persists exactly one `thread_id` in `localStorage`
(`src/thread.ts`) and the sidebar renders a single static entry
(`src/nav.ts:recentConversations`). Clicking "New chat" overwrites that id, so
previous conversations are unreachable from the UI even though the Runtime
still stores them.

The Runtime already provides everything needed:

- Agno AgentOS exposes `GET /sessions`, `POST /sessions/{id}/rename`, and
  `DELETE /sessions/{id}` out of the box.
- AG-UI's `thread_id` is mapped directly to Agno's `session_id`
  (`agno/os/interfaces/agui/router.py`), so the existing `HttpAgent({ threadId })`
  wiring resumes any historical session without changes.
- `user_isolation=True` scopes session list/read/write to the JWT subject;
  the ordinary `user` role already includes `sessions:read/write/delete`.

This milestone is therefore pure frontend work: consume the existing API,
replace the static navigation data with live state, and manage the active
`threadId` so switching sessions remounts the CopilotKit provider correctly.

## 3. Scope

### 3.1 In Scope

1. **Runtime session API client**
   - Add a small `src/sessions-api.ts` module on top of the existing shared
     `runtimeRequest` helper (`src/lib/runtime-api.ts`).
   - Type the subset of `SessionSchema` the UI needs: `session_id`,
     `session_name`, `created_at`, `updated_at`.
   - `getSessions({ page, limit, signal })` calls
     `GET /sessions?type=agent&component_id=team-leader&sort_by=updated_at&sort_order=desc`.
   - `renameSession(sessionId, name, signal)` and `deleteSession(sessionId, signal)`
     call the corresponding Agno endpoints.

2. **Dynamic recent-conversations sidebar**
   - Replace the static `recentConversations` array in `src/nav.ts` with a
     component-driven list fed by `getSessions`.
   - Show `session_name` when present; fall back to a localized "Untitled
     conversation" label otherwise.
   - Highlight the entry whose `session_id` matches the active `threadId` when
     that session exists in the Runtime-backed list.
   - Clicking an entry switches the active thread and returns to the chat view.
   - Render loading, empty, and error states using existing UI conventions.

3. **Active-thread management**
   - Keep `threadId` as the single source of truth in `src/app.tsx`.
   - Switching sessions calls `setThreadId(sessionId)` and relies on the
     existing `key={threadId}` remount to replay history through AG-UI.
   - Persist the active id with the existing `loadThreadId` / `resetThreadId`
     helpers so a page reload restores the last viewed session.

4. **New conversation flow**
   - "New chat" generates a fresh id, updates `localStorage`, and remounts the
     chat surface, but **does not add an entry to the sidebar yet**.
   - The new conversation is inserted at the top of the sidebar **only after
     the first message exchange has been persisted by the Runtime**. Refresh
     the session list at that point so the new session appears with its real
     `session_name` and `updated_at`, matching mainstream tools such as
     DeepSeek.

5. **Rename and delete actions**
   - Add per-session inline or dropdown actions in the sidebar.
   - Rename uses `POST /sessions/{id}/rename`; update the list optimistically
     or refetch on success.
   - Delete uses `DELETE /sessions/{id}` with a confirmation step. If the
     active session is deleted, reset to a new thread.

6. **Documentation and versioning**
   - Update `docs/frontend-architecture.md` with the session-list data flow and
     the `thread_id` ↔ `session_id` relationship.
   - Update `AGENTS.md`: current milestone v0.4.0 and move conversation history
     out of the deferred scope.
   - Add any new `common` namespace i18n keys.
   - Bump `package.json` to `0.4.0`.

### 3.2 Out of Scope

- Runtime or Agno implementation changes.
- Session search, archiving, tagging, or export.
- Infinite scroll / virtualized session list; simple pagination or a "load
  more" button is sufficient if needed.
- Router library or deep links to individual sessions.
- Admin console changes; admins still see no chat surface.
- Cross-device conflict resolution or offline session caching.

## 4. Success Criteria

- [ ] The sidebar lists the current user's recent agent sessions, newest
  activity first, with loading/empty/error states.
- [ ] Clicking a historical session loads its full message history through the
  existing AG-UI replay flow and allows continuing the conversation.
- [ ] "New chat" clears the chat surface without adding a sidebar entry; the
  new conversation appears at the top of the sidebar only after its first
  message exchange is persisted, and previous conversations remain accessible.
- [ ] Reloading the page restores the last active session and its history.
- [ ] A session can be renamed and the new name is reflected immediately.
- [ ] A session can be deleted after confirmation; deleting the active session
  resets the chat to a new thread.
- [ ] Ordinary users only see their own sessions; no admin-only data is exposed.
- [ ] `npm run lint`, `npm run typecheck`, and `npm run build` pass.

## 7. Manual Verification (owner walkthrough)

Prerequisites:

1. Runtime v0.6.2+ is running with real Logto-issued JWTs and user isolation.
2. Logto has at least one ordinary `user` test account.
3. Start this app with `npm run dev` on port 3000.

Walkthrough:

1. Sign in as `user` and click "New chat". Confirm the chat surface clears and
   no new sidebar entry appears yet. Send a message, then confirm the new
   conversation is inserted at the top of the sidebar. Create two or three more
   conversations the same way.
2. Click an older session → its history replays and you can continue the
   conversation.
3. Reload the page → the last active session is restored.
4. Rename a session → the sidebar updates.
5. Delete a non-active session → it disappears. Delete the active session →
   chat resets to a new thread.
6. Sign in as a different ordinary user → only that user's sessions are listed.
7. Run `npm run lint`, `npm run typecheck`, and `npm run build`.
