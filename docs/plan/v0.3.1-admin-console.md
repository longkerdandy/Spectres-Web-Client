## 2. Context

The Runtime's v0.6.2 milestone makes Logto the owner of users, roles, and
assignments. Its `admin` role carries `agent_os:admin`; its ordinary `user`
role does not. Runtime remains the authorization boundary and retains the
admin's full API break-glass.

The Client has a different product responsibility: presentation. An admin
should see only a management console, not the AI assistant. This is not a
second authorization layer and does not remove any backend capability.

The current Runtime contract shapes the page in four important ways:

- `GET /info` is public and returns `name`, `os_version`, `agno_version`,
  `auth_mode`, and `user_isolation`. `os_version` is the AgentOS instance
  version (currently the framework default), not the Spectres Runtime
  milestone version; the UI must label it accurately. `/info` is sufficient
  for this page, so `/config` is not needed.
- `GET /users` is admin-only and paginated as `{data, meta}` (20 items per
  page by default). Rows contain `id`, `name`, `email`, `status`, and
  `disabled`. The directory is JIT-provisioned: a Logto user appears only
  after their first valid Runtime request; this is not a complete Logto
  account list.
- Runtime does not mirror Logto roles into this directory. Do not present
  `role_slug`/`role_name` as Logto roles or add a role column to this page.
- `PATCH /users/{user_id}` with `{"disabled": true|false}` controls only
  Runtime access. Disabling denies the next request even with a valid token;
  it does not suspend/delete the Logto account or revoke its tokens.

The implementation stays within current project conventions:

- static SPA, no backend/BFF;
- no router library — the existing local `ViewId` state model is sufficient;
- no state-management library and no new test framework;
- existing Logto SDK, shell, shadcn components, and token-getter plumbing are
  reused;
- the first admin page is intentionally small, not a dashboard framework.

## 3. Scope

### 3.1 In Scope

1. **Runtime-scope reader and role state**
   - Extend the existing auth plumbing (`src/auth.ts` and the auth-gate
     boundary) to obtain the current API-resource access token through
     `@logto/react` and safely decode `scopes` and `sub` from its payload.
   - Model role resolution explicitly as `loading | user | admin`; derive
     `isAdmin` from `scopes.includes("agent_os:admin")`. After a token has
     been obtained, a missing/malformed claim resolves to `user`, but an
     unresolved initial token must not be treated as `user`.
   - Keep one in-memory role state owner at the auth-gate boundary. Publish
     the claims whenever the shared token getter obtains a token, including
     an SDK-refreshed token, so role changes follow refresh/re-login without
     a second token store or polling loop.
   - Client-side decoding controls presentation only; it is never treated as
     proof of permission. Do not persist decoded tokens, scopes, or role
     state outside the Logto SDK.

2. **Role-specific top-level experience**
   - While role state is `loading`, render only the existing shared loading
     screen. Do not mount either role's product surface during this phase;
     this prevents a cold admin load from briefly mounting chat and issuing
     `/agui` before the token is parsed.
   - In `app.tsx`, render `AdminPage` instead of the chat/extension experience
     for `admin`. Ordinary `user` accounts follow the current path with no
     admin link or admin view.
   - Admin mode renders no `ChatPage`, CopilotKit provider, thread agent, or
     extension surface and makes **zero `/agui` requests**. Hiding a chat button
     alone is insufficient. A role transition unmounts the old surface before
     mounting the new one.
   - Preserve the existing callback and sign-out flows. No router or
     deep-link work: this is a role-selected view, not a new routing system.

3. **Shared Runtime API plumbing**
   - Extract the Runtime base-URL derivation and generic Bearer-token request
     handling from the ETF Grid extension into a small core API module reused by
     both the extension and `AdminPage`; do not hard-code `localhost` or create
     a second HTTP/auth stack.
   - Keep ETF Grid's unified-422 mapping in the extension. The shared layer
     handles JSON errors, one 401-driven re-auth path, and non-retrying 403
     errors. Admin list/update requests support cancellation and pending
     states so stale responses cannot overwrite a newer role/view.

4. **Minimal `AdminPage`**
   - Add one focused page/component using existing shadcn primitives and the
     current shell/user area.
   - **System overview**: show Runtime `name`, clearly labelled AgentOS
     `os_version`, Agno `agno_version`, `auth_mode`, and `user_isolation`
     from `/info`. Do not call `/config` or imply that `os_version` is the
     Spectres Runtime release version.
   - **Directory users**: explain that these are Runtime directory users,
     not all Logto accounts. Request
     `/users?include_disabled=true&page=<n>&limit=20`, render
     name/email/status (falling back to `id`), and use `meta` for simple
     previous/next pagination. Do not infer Logto roles from this response.
   - **Enable/disable**: call `PATCH /users/{user_id}` with only `disabled`.
     Confirm the target before disabling, disable the action for the current
     token's own `sub` to prevent self-lockout, and show per-row pending and
     failure states. Update from the returned row or refresh the current page
     without discarding pagination.
   - Explain that disabling blocks Runtime immediately but does not suspend
     the Logto account or revoke tokens. Show loading, empty, request-error,
     and 403 states using existing UI conventions.
   - Link to Logto Console for account creation, roles, and assignments via
     a new `VITE_LOGTO_ADMIN_ENDPOINT` setting (local default
     `http://localhost:3002`); do not derive the Console URL from the OIDC
     endpoint or reproduce those features locally.

5. **Documentation and versioning**
   - Update `docs/frontend-architecture.md` with role-derived views, the
     loading/security boundary, directory semantics, and Runtime API surface.
   - Update `AGENTS.md`: current milestone v0.3.1 and remove/adjust the
     earlier role-based-UI exclusion.
   - Update `.env.example` and README for `VITE_LOGTO_ADMIN_ENDPOINT` and the
     Runtime-directory versus Logto-account distinction.
   - Bump `package.json` to `0.3.1`.

6. **Manual verification**
   - Verify both roles against real Logto + Runtime, including a cold admin
     load and network inspection proving admin makes zero AG-UI calls.
   - Verify enable/disable on a disposable, already-provisioned directory
     user and restore the desired final state. Never test by disabling the
     sole administrator; also verify the UI prevents self-disable.
   - Verify role changes in both directions after token refresh or re-login,
     including that the old role's surface unmounts cleanly.

### 3.2 Out of Scope

- **All Runtime and Logto implementation** — owned by Runtime v0.6.2.
- Router libraries, admin deep links, new state management, or a new test
  framework.
- Role/permission editors, user creation, user search, a Logto-role column,
  or another Logto Console.
- General system-settings editing, charts, audit dashboards, chat-history
  inspection, or a full-featured admin framework.
- Extension UI/authorization changes and ordinary chat/extension redesign
  beyond extracting the shared Runtime API plumbing.
- Backend denial of admin's Agno superuser API capabilities.

## 4. Success Criteria

- [ ] A cold real `admin` login renders only the management console; role
  resolution never briefly mounts chat, normal-user navigation is absent,
  and no `/agui` request occurs.
- [ ] A real ordinary `user` login keeps the current chat experience and has
  no way to open the admin view; after token resolution, missing/malformed
  scopes fail to non-admin.
- [ ] System overview uses the actual `/info` fields with accurate version
  labels; `/users` handles `{data, meta}` and pagination when multiple pages
  exist. Loading/empty/error/403 states are understandable.
- [ ] Admin can disable and re-enable a disposable directory user through
  `PATCH /users/{user_id}`; Runtime denies the disabled user's valid token
  immediately, the UI explains the Logto boundary, and self-disable is not
  offered.
- [ ] Logto role changes in both directions are reflected after token
  refresh or re-login, with the old role's surface fully unmounted.
- [x] `npm run lint`, `npm run typecheck`, and `npm run build` pass.

## 7. Manual Verification (owner walkthrough)

Prerequisites:

1. Runtime v0.6.2 is running with real Logto-issued `scopes` arrays, and
   `VITE_LOGTO_ADMIN_ENDPOINT` points to the Logto Console.
2. Logto has one `admin` and one ordinary `user` test account plus a
   disposable ordinary account. Sign in as the disposable user and make one
   valid Runtime request first so JIT provisioning adds it to `/users`.
3. Start this app with `npm run dev` on port 3000.

Walkthrough:

1. Sign in as `user` → existing chat loads; no admin navigation appears.
2. Open a fresh browser session and sign in as `admin` → only the management
   console loads. Confirm the loading phase never flashes chat and DevTools
   Network records zero `/agui` requests. Check the `/info` labels and the
   directory explanation; if multiple pages exist, exercise previous/next.
3. Confirm the current administrator's disable action is unavailable. For
   the disposable user, disable → verify that user's still-valid token is
   rejected by Runtime → re-enable → verify access recovers. Confirm the UI
   distinguishes Runtime disablement from Logto suspension/token revocation.
4. Open the configured Logto Console link and confirm account/role
   management remains there; no duplicate role editor or misleading role
   column exists in this app.
5. Change a test account from `user` to `admin`, refresh its access token
   (or sign in again), and verify chat unmounts before the console appears.
   Repeat from `admin` to `user` and verify the console unmounts without
   leaking admin requests.
6. Restore/disable-delete only disposable test state as appropriate; never
   target the sole administrator.
7. Run `npm run lint`, `npm run typecheck`, and `npm run build`.
