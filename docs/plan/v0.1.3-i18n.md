## 2. Context

All UI copy is currently hardcoded Chinese in four places:

- `src/nav.ts` — sidebar navigation ("新聊天", "定时任务", "插件", "当前会话", …)
- `src/components/app-shell.tsx` — "最近", "本地单用户"
- `src/plugins/etf-grid/index.ts` — plugin nav label "ETF 网格"
- `src/plugins/etf-grid/grid-page.tsx` — placeholder page title/description

Additionally, the CopilotKit chat surface renders its own default English labels (`CopilotChatDefaultLabels`: input placeholder, toolbar tooltips, disclaimer, welcome message), which must come from the same i18n layer so a future locale switches the whole UI consistently.

Approaches were surveyed before settling on this design:

- **react-i18next** (chosen): the React mainstream. Mature interpolation/pluralization/fallback, `useTranslation` works cleanly with React 19 strict mode, and its **namespace** model maps 1:1 onto the plugin architecture — each plugin owns a namespace and ships its own locale files inside its directory, discovered by the same build-time glob mechanism as the plugin manifests. Adding a plugin with copy never touches platform code.
- **Zero-dependency hand-rolled** (React Context + dictionary objects, ~60 lines): rejected. It fits the minimalism principle at today's ~70 strings, but plural rules, fallback chains, and key type-safety would be rebuilt by hand, and copy volume grows fast in v0.2.x (grid page, chat tool cards) — the wheel-reinvention cost lands exactly when the milestone load is highest.

Key constraints and decisions:

- **English-only UI this milestone.** `en` is the sole entry in the supported-languages list, the default, and the fallback. All existing Chinese copy is **translated into English** in the resource files; no Chinese resources ship yet. zh-CN is re-added later as a follow-up milestone (the original copy is preserved in git history).
- **Infrastructure is built complete, not English-only.** Language resolution order (`localStorage` → `navigator.language` → fallback) and the plugin locale-file convention are implemented now, so a future locale is a pure data addition.
- **No language switcher UI yet.** With one supported language there is nothing to switch; the switcher (sidebar footer dropdown) arrives together with the second locale.
- **Namespaces**: `common` for the core shell (nav, user area, shared strings, chat labels); each plugin gets a namespace equal to its plugin id (`etf-grid`), referenced as `t("etf-grid:nav.title")`.
- **Data files stop holding copy.** `src/nav.ts` and plugin manifests carry translation **keys**, not text; rendering components resolve them with `t()`.
- **CopilotKit labels** are fed from the i18n layer: v2 exposes `labels?: Partial<CopilotChatLabels>` on `CopilotChat`, mapped from `t()` in `chat-page.tsx`.
- **Custom minimal language detection** (~15 lines, localStorage + `navigator.language`) instead of adding `i18next-browser-languagedetector` as a third dependency.
- **New dependencies**: `i18next` + `react-i18next` (both MIT). Nothing else.

### 2.1 Plugin Locale Loading

Plugin copy raises a question the core shell does not: **how do plugin locale bundles get discovered and registered without the platform hardcoding each plugin?** The design follows the same pattern as plugin UI discovery in v0.1.2 — one scan entry point, everything else flows through the typed manifest:

1. **Locales are a manifest contribution, not a second platform-side glob.** The platform's only scan of `src/plugins/` remains the registry's `import.meta.glob("./*/index.ts")`. Each plugin bundles its own locale files inside its `index.ts` with the same eager, build-time mechanism used for views:

   ```ts
   // src/plugins/etf-grid/index.ts
   export default definePlugin({
     id: "etf-grid",
     contributes: {
       navItems: [/* … */],
       views: [/* … */],
       locales: defineLocales(
         import.meta.glob("./locales/*.json", { eager: true, import: "default" }),
       ),
     },
   });
   ```

   `contributes.locales` is a new **optional** field in the extension-point bag — the exact growth path v0.1.2 established for future contribution types like `toolCards`. Plugins without copy simply omit it; existing plugins are unaffected. `defineLocales()` (in `src/plugins/types.ts`, next to `definePlugin`) normalizes glob paths to language codes (`./locales/en.json` → `en`) and enforces the `Record<language, bundle>` shape at compile time.
2. **The plugin id stays the single source of truth for the namespace.** Because bundles arrive via the manifest, the i18n layer registers them under the manifest's declared `id` — no path-derived plugin id that could silently drift from the declared one.
3. **Registration happens inside `i18next.init()`, not after it.** The i18n module reads `plugins` from the registry and folds every manifest's `locales` into a single `resources` object (`{ en: { common: …, "etf-grid": … } }`) passed to `init()` together with the core `common` bundle. This makes resource loading synchronous, atomic, and ordering-independent — no `addResourceBundle` at module scope, no import-ordering hazard, no flash of raw keys on first paint. The dependency direction is `i18n → registry → manifests → views → react-i18next`; plugin code imports `useTranslation` from `react-i18next` directly and never imports `src/i18n`, so there is no import cycle.
4. **All supported languages are registered up front, so runtime switching is synchronous.** When a second locale ships, both languages' bundles for every plugin are already in memory; `i18next.changeLanguage()` re-renders instantly with no async fetch and no loading state. A plugin may even ship locale files for not-yet-supported languages — languages outside `SUPPORTED_LANGUAGES` are ignored at init and picked up automatically once the language is enabled.
5. **Initialization completes before React renders.** `main.tsx` awaits (or synchronously runs) i18n setup before `createRoot().render()`, guaranteeing every `t()` call in the tree resolves against a fully populated store.
6. **Lazy/code-split loading is the documented evolution path, not the current mechanism.** A plugin's glob without `eager: true` returns lazy loaders that Vite code-splits into async chunks; bundles would then be loaded on `languageChanged` or plugin-view mount and registered via `addResourceBundle`. Deferred for the same reason v0.1.2 deferred plugin code splitting — bundle size does not force it yet, and eager loading keeps language switching synchronous and the mental model simple.

## 3. Scope

### 3.1 In Scope

1. **i18n core** (`src/i18n/index.ts`)
   - i18next + `initReactI18next` initialization. Core copy lives in the `common` namespace bundled from `src/i18n/locales/en/common.json`.
   - **Plugin locale registration** (per §2.1): reads `plugins` from the registry and folds each manifest's `contributes.locales` into the `resources` object passed to `init()`, namespaced by the manifest's `id`. Languages outside `SUPPORTED_LANGUAGES` are ignored.
   - `SUPPORTED_LANGUAGES` constant (`["en"]` now), language resolution order `localStorage("spectres:lang")` → `navigator.language` → `"en"`, and persistence of the resolved language.
   - Reactive `document.documentElement.lang` sync; `<html lang>` in `index.html` set to `en` as the static default.
   - `main.tsx` completes i18n setup before rendering the React tree.

2. **Core shell migration**
   - `src/nav.ts`: `label` / `badge` / `title` fields become translation keys (e.g. `nav.newChat`, `nav.scheduledTasks.badge`).
   - `src/components/app-shell.tsx`: renders via `useTranslation("common")`; the "最近" group label and "本地单用户" user-area string become keys.

3. **Plugin contract changes** (`src/plugins/types.ts`)
   - `PluginNavItem.label` → `labelKey`.
   - New optional `contributes.locales` extension-point field + the `defineLocales()` helper that normalizes a plugin-local `import.meta.glob("./locales/*.json", …)` result into `Record<language, bundle>` and enforces the shape at compile time.
   - The registry attaches each nav item's plugin namespace (manifest `id`) during aggregation, so the shell renders `t(`${namespace}:${labelKey}`)` without knowing plugin internals. Registry discovery itself is unchanged — the `./*/index.ts` glob remains the platform's only scan entry point.

4. **`etf-grid` plugin migration**
   - `src/plugins/etf-grid/locales/en.json`: nav label, page title, description, empty-state copy — translated to English.
   - Manifest declares `locales` via `defineLocales(...)` and uses `labelKey`; `grid-page.tsx` renders via `useTranslation("etf-grid")`.

5. **CopilotKit chat labels**
   - `chat-page.tsx` passes `labels` (input placeholder, welcome message, disclaimer, toolbar tooltips) mapped from `common` namespace keys, so chat UI copy follows the active language.

6. **Docs & versioning**
   - Update `docs/frontend-architecture.md`: i18n conventions — how to add a string, how namespaces map to plugins, how to add a new language later.
   - Update `AGENTS.md` §3.2 milestone status.
   - Bump `package.json` version to `0.1.3`.

### 3.2 Out of Scope

- **Non-English locales** — zh-CN (and any other language) is a later follow-up; only `en` ships.
- **Language switcher UI** — arrives with the second locale.
- **Type-safe translation keys** (`i18next-resources-for-ts` or generated types) — revisit if key drift becomes a problem.
- **ICU MessageFormat / `react-intl`-style rich formatting** — i18next's built-in interpolation and plural forms are sufficient.
- **Lazy-loading locales over HTTP** — all resources are bundled statically; the app is a static SPA with no locale server.
- **Per-language code splitting of locale bundles** (non-eager glob + `addResourceBundle` on language switch) — the documented evolution path in §2.1 item 6; deferred until bundle size forces it.
- **Date/number/currency formatting** (`Intl.*` helpers) — no UI needs it yet; add per-milestone when v0.2.0's grid UI requires it.
- **Tests** — manual verification per milestone walkthrough, as before.
