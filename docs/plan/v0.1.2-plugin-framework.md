## 2. Context

The v0.1.1 shell ships with a hardcoded, disabled "ETF 网格" entry in `src/nav.ts`. The Runtime side already has an extension mechanism (`spectres/extensions/` packages with `name` + `register(ctx)`, discovered via `pkgutil`), and more Runtime extensions will follow — the client needs its own plugin mechanism instead of hand-editing the nav registry each time.

Approaches were surveyed before settling on this design:

- **Build-time plugin registry** (Vue/React ecosystem mainstream, via Vite's `import.meta.glob`): chosen as the discovery mechanism — simple, type-safe, zero runtime cost, works in a static SPA.
- **Extension-point model** (Backstage's New Frontend System): chosen as the contribution structure — the platform defines typed extension points and plugins declare contributions to them. Adding a new contribution type later (e.g. chat tool cards in v0.2.1) never touches existing plugins.
- **Runtime loading** (Module Federation, Grafana-style manifest + remote modules): explicitly rejected — it solves independent-deployment and marketplace problems this project does not have (single user, single repo, plugins ship with the app).

Key constraints and decisions:

- **Plugin = one self-contained directory** under `src/plugins/<id>/`, holding its own views, API client, types, and components. Nothing about a plugin lives outside its directory except its directory.
- **Contract**: `definePlugin({ id, contributes })` where `contributes` is an extension-point bag: `navItems` (sidebar Plugins group) and `views` (main-area pages) now; `toolCards` arrives in v0.2.1 as a new optional field with zero changes to existing plugins.
- **Discovery**: `import.meta.glob("./*/index.ts", { eager: true })` in `src/plugins/index.ts`. Presence in the tree is the opt-in (mirroring the Runtime's "no enable/disable gating"); a broken plugin fails typecheck/build — fail-loud, never silently degraded.
- **Plugin id matches the Runtime extension name** (`etf-grid` ↔ `etf_grid`), keeping a 1:1 mental model across the layers.
- **No `PluginContext` yet**: endpoint derivation / shared services are injected when v0.2.0's API client actually needs them (YAGNI for a blank page).
- **The blank ETF Grid page is in scope**: the hardcoded disabled nav entry is removed and replaced by a real plugin whose view is a placeholder page — this validates the whole chain (discovery → nav → view switch) before v0.2.0 builds the real UI.

The tech stack is unchanged (Vite + React 19 + TypeScript + Tailwind + shadcn/ui + CopilotKit). No new dependencies.

## 3. Scope

### 3.1 In Scope

1. **Plugin contract** (`src/plugins/types.ts`)
   - `PluginDefinition` (`id`, `contributes`), `PluginContributions` (`navItems?`, `views?`), and the `definePlugin()` helper enforcing the shape at compile time.

2. **Plugin registry** (`src/plugins/index.ts`)
   - Build-time discovery via `import.meta.glob` (eager).
   - Aggregation by extension point: `navItems()`, `viewFor(id)`.

3. **Shell integration**
   - The sidebar's Plugins group renders children from the registry instead of `src/nav.ts`.
   - `app.tsx` resolves the active view from registry-contributed views; `ViewId` widens from the `"chat"` literal to core views + plugin view ids.
   - The hardcoded disabled "ETF 网格" entry is removed from `src/nav.ts`.

4. **First plugin: `etf-grid` (blank page)**
   - `src/plugins/etf-grid/index.ts` (manifest) + a placeholder `GridPage` view (page title, short description, "under construction" empty state built with shadcn/ui components).
   - Its nav item is **enabled** — clicking it switches the main area to the blank page; the chat thread is unaffected.

5. **Docs & versioning**
   - Update `docs/frontend-architecture.md` (plugin framework: contract, discovery, extension points, how to add a plugin).
   - Update `AGENTS.md` §3.2 milestone status.
   - Bump `package.json` version to `0.1.2`.

### 3.2 Out of Scope

- **Any real ETF Grid functionality** (API client, status table, ledger) — v0.2.0 fills the blank page.
- **`toolCards` extension point** — arrives with v0.2.1's chat cards.
- **`PluginContext` / endpoint injection** — lands with v0.2.0's API client.
- **Enable/disable gating** (`VITE_ENABLED_PLUGINS`) — presence in the tree is the only switch for now.
- **Lazy loading / code splitting** — eager glob; revisit when bundle size forces it.
- **npm-distributed third-party plugins** — the Runtime's `entry_points` analogue, deferred indefinitely.
- **Tests** — manual verification per milestone walkthrough, as before.

## 4. Success Criteria

- [ ] The ETF 网格 sidebar entry comes from the plugin's own directory, not from `src/nav.ts`; it is enabled and switches the main area to the blank plugin page.
- [ ] The shell contains no ETF-Grid-specific code: adding a new plugin is "create a directory with `index.ts` + view" with zero edits outside it (verified by code review).
- [ ] Switching between chat and the plugin page does not reset the chat thread.
- [ ] Fail-loud: a plugin manifest with a wrong shape fails `npm run typecheck`.
- [ ] `npm run lint` and `npm run typecheck` pass.
- [ ] The app builds to static files and works served from `dist/`.
