## 2. Context

The Runtime's first extension, `etf_grid` (MA60-anchored, 5%-step ETF grid trading assistant), is nearing completion: the domain core shipped in Runtime v0.4.0, and the API & Toolkit milestone (v0.4.1) exposes four Agent tools on the Team Leader plus six REST endpoints under `/api/v1/extensions/etf-grid/`. The Runtime's extension architecture doc (`runtime-extensions.md` §7) defines a two-part **Client contract**:

1. **Standalone page** (this milestone): a pure-React grid status & ledger page that calls the REST API directly (`GET /status` as the primary data source).
2. **In-chat tool cards** (moved to [v0.2.1](v0.2.1-etf-grid-chat-tool-cards.md)): custom renderers for the four stable AG-UI tool names.

Key constraints and decisions:

- **Runtime dependency**: v0.4.1 (`etf_grid` API & tools) must be merged and live-verified on the Runtime side before the joint acceptance walkthrough of this milestone. Until then, development proceeds against the documented API contract.
- **REST for the standalone page**: the page calls the extension's HTTP API directly, same origin as `VITE_AGENT_ENDPOINT`. The API base URL is **derived** from `VITE_AGENT_ENDPOINT` (strip the `/agui` path, append `/api/v1/extensions/etf-grid`); no new environment variable is introduced.
- **No HITL yet**: the Runtime has not wired `requires_confirmation` for `record_grid_trade`. The page mitigates mis-entry with a local amount preview (gross/commission/net) and a confirm step before `POST /trades`; the in-chat confirmation UX remains deferred (see v0.2.1 Out of Scope).
- **Minimalism**: no router library yet. With exactly two views (chat, grid), view switching is plain React state in the app shell. A router is introduced when a milestone adds deep-linking or more pages.
- **Data shapes**: all monetary/Decimal values arrive as strings; dates are ISO strings. The client parses and formats at the presentation layer and never does float math on money.

The tech stack is unchanged: Vite + React 19 + TypeScript (strict) + Tailwind CSS 4 + CopilotKit React SDK. No new runtime dependencies are planned.

## 3. Scope

### 3.1 In Scope

1. **ETF Grid API client module**
   - Typed `fetch` wrappers for the six extension endpoints (`GET /status`, `GET /signals`, `POST /signals/compute`, `POST /sync`, `GET /trades`, `POST /trades`).
   - Base URL derived from `VITE_AGENT_ENDPOINT` at a single point.
   - TypeScript types mirroring the Runtime's JSON contract (stringified Decimals, ISO dates, `orders[]`, `block_reason`, gate fields).

2. **Grid view on the plugin framework**
   - The ETF Grid page fills in the blank plugin view shipped by [v0.1.2](v0.1.2-plugin-framework.md) (`src/plugins/etf-grid/`): API client, types, and page components live inside the plugin directory; the shell is untouched.
   - Chat remains the default view; the existing `thread_id`/`CopilotKit` behavior is untouched.

3. **Grid status page**
   - Per-symbol status table: holdings (shares, avg cost, realized P&L), latest close/market value, current level vs. anchor MA60, gate state (`gate_closed`, `gate_percentile`, `block_reason`).
   - Signal orders render as a **two-sided bracket** mirroring the Runtime's `orders[]` semantics (`core/grid.py` `compute_signal`): a pending buy leg and a pending sell leg are normally both present every day, plus a triggered order (single side) on level-change days. Each leg shows side, limit price, grids, and kind (`triggered` / `pending`) with `note` badges (`cost_protection`, `gate_closed`); a missing leg is explained (e.g. no position), never silently omitted. Layout reference: `docs/design/v0.2.0-grid-page-mockup.html`.
   - **Refresh data** action (`POST /sync`) with per-source row counts and partial-failure (`errors`) surfacing; **Recompute signals** action (`POST /signals/compute`).

4. **Trade ledger**
   - Full-width filterable trade list (`GET /trades`: symbol, date range, limit) with all amount columns (gross, commission, net), rendered as a table.
   - **Record trade** as a modal opened from the ledger header (`POST /trades`): symbol, date, side, price, quantity, commission rate, note; local preview of gross/commission/net computed from the inputs; explicit confirm step before submission; inline display of 422 validation errors.

5. **Presentation plumbing**
   - Shared formatting helpers (money/percent/date display from string inputs), loading and error states for every async surface.
   - Empty states (no trades, no signals, Runtime unreachable).

6. **Docs & versioning**
   - Update `docs/frontend-architecture.md` (new views, API client layer).
   - Update `AGENTS.md` §3.2 milestone status and §3.3 out-of-scope items that this milestone absorbs.
   - Bump `package.json` version to `0.2.0`.

### 3.2 Out of Scope

- **In-chat custom tool cards** for the four grid tools — moved to [v0.2.1](v0.2.1-etf-grid-chat-tool-cards.md).
- **Signal history section on the page** — dropped by owner decision during layout review; historical signals remain available via the chat tools (v0.2.1) and `GET /signals` if ever needed.
- **HITL confirmation UX in chat** for `record_grid_trade` — deferred until the Runtime adopts Agno `requires_confirmation` (shared HITL path, Runtime ADR 0003 / architecture §6).
- **Proactive signal notifications / updates stream** — belongs to a later automation milestone (Runtime ADR 0003).
- **A router library**, deep-linking, and browser-history integration — deferred until more pages force it.
- **Thread list / management** UI — a separate milestone.
- **Per-Slave visibility and custom AG-UI events** — Runtime ADR 0004 phase 2+.
- **Authentication** — single-user local deployment (Runtime ADR 0005).
- **Charts / visualizations** (price with grid levels, equity curve) — candidate for a follow-up milestone once the base page proves out.
- **Tests** — still manual verification per milestone walkthrough; the test framework lands in a later milestone.

## 4. Success Criteria

- [ ] The Grid view renders live status for every configured ETF symbol from `GET /status`, with holdings, latest signal orders, and gate state all visible.
- [ ] **Refresh data** triggers a sync and reports per-source results; a partial failure (e.g. one source down) is surfaced as a warning, not a page crash.
- [ ] The trade ledger shows all amount columns (gross, commission, net) and filters by symbol and date range.
- [ ] A trade recorded through the ledger form (with preview + confirm) appears in the trade list after refresh, and the Runtime echoes matching gross/commission/net.
- [ ] Invalid trade input shows the Runtime's 422 validation messages inline; no silent failures.
- [ ] Switching between Chat and Grid views does not reset the chat thread.
- [ ] `npm run lint` and `npm run typecheck` pass.
- [ ] The app still builds to static files and works served from `dist/`, configured solely via `VITE_AGENT_ENDPOINT`.
