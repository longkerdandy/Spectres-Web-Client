## 2. Context

The Runtime's first extension, `etf_grid` (MA60-anchored, 5%-step ETF grid trading assistant), shipped its domain core in Runtime v0.4.0 and its four Agent tools plus six REST endpoints under `/api/v1/extensions/etf-grid/` in v0.4.1 (completed and live-verified). Runtime **v0.4.4 (API hardening)** then closed the two contract gaps found in this milestone's pre-implementation audit: list endpoints now return a pagination envelope, and all 422s share one error shape. The Runtime's extension architecture doc (`runtime-extensions.md` §7) defines a two-part **Client contract**:

1. **Standalone page** (this milestone): a pure-React grid status & ledger page that calls the REST API directly (`GET /status` as the primary data source).
2. **In-chat tool cards** (moved to [v0.2.1](v0.2.1-etf-grid-chat-tool-cards.md)): custom renderers for the four stable AG-UI tool names.

Key constraints and decisions:

- **Runtime dependency**: Runtime v0.4.4 ([`v0.4.4-etf-grid-api-hardening.md`](../../Spectres-Runtime/docs/plan/v0.4.4-etf-grid-api-hardening.md)) defines the API contract this milestone builds against — development proceeds against the documented contract; the joint acceptance walkthrough runs against a live Runtime with v0.4.4 deployed.
- **REST for the standalone page**: the page calls the extension's HTTP API directly, same origin as `VITE_AGENT_ENDPOINT`. The API base URL is **derived** from `VITE_AGENT_ENDPOINT` (strip the `/agui` path, append `/api/v1/extensions/etf-grid`); no new environment variable is introduced. CORS is app-wide on the Runtime (AgentOS `CORSMiddleware`), so the extension routes are covered by the same `CORS_ALLOWED_ORIGINS` already used for `/agui`.
- **API contract details** (verified against the Runtime working tree, 2026-10-12):
  - `GET /status` returns a list per symbol. Holdings/close fields sit at the top level; **level, anchor MA60, gate state, and `orders[]` are nested under `signal`**, which is **null before the first signal compute** — the page must render an explicit empty state, and `avg_cost` / `close` / `market_value` are nullable too.
  - `block_reason` has **four** values: `gate_closed | max_grids_reached | cost_protection | no_position`. Missing order legs are normal (no position → no pending sell; bottom level → no pending buy; gate-blocked → no triggered order, only `block_reason`) and must be explained, never silently omitted.
  - `POST /trades` takes **`trade_date`** (not `date`), returns **201** with the persisted row (system-computed `gross_amount`/`commission`/`net_amount`).
  - `POST /sync` returns per-source results: `candles` row counts are **grouped by symbol**; failed sources are `null` with messages in `errors`.
  - `GET /trades` and `GET /signals` return the v0.4.4 **pagination envelope** `{"items": [...], "total": int, "limit": int, "offset": int}`; `limit` defaults to 20 and is validated (`1..200`), invalid `limit`/`offset` → 422.
  - Every 422 from the router has `detail` as a **list of objects carrying `loc` / `msg` / `type`** (extra keys like `input`/`url` may be present; the client ignores them) — one rendering path for pydantic and domain rejections alike.
- **i18n (v0.1.3 layer)**: all page copy — table headers, actions, empty states, error text, modal — lives as keys in `src/plugins/etf-grid/locales/en.json` and is rendered via `useTranslation("etf-grid")`. No hardcoded UI strings; the v0.1.3 conventions apply to everything this milestone adds.
- **No HITL yet**: the Runtime has not wired `requires_confirmation` for `record_grid_trade`. The page mitigates mis-entry with a local amount preview (gross/commission/net) and a confirm step before `POST /trades`; the in-chat confirmation UX remains deferred (see v0.2.1 Out of Scope).
- **Minimalism**: no router library yet. With exactly two views (chat, grid), view switching is plain React state in the app shell. A router is introduced when a milestone adds deep-linking or more pages.
- **Data shapes**: all monetary/Decimal values arrive as strings; dates are ISO strings. The client parses and formats at the presentation layer and never does float math on money.

The tech stack gains no new runtime dependencies: Vite + React 19 + TypeScript (strict) + Tailwind CSS 4 + CopilotKit React SDK + the i18n layer shipped in v0.1.3.

## 3. Scope

### 3.1 In Scope

1. **ETF Grid API client module** (inside `src/plugins/etf-grid/`)
   - Typed `fetch` wrappers for the six extension endpoints (`GET /status`, `GET /signals`, `POST /signals/compute`, `POST /sync`, `GET /trades`, `POST /trades`).
   - Base URL derived from `VITE_AGENT_ENDPOINT` at a single point.
   - TypeScript types mirroring the Runtime's JSON contract per §2: stringified Decimals, ISO dates, nullable `signal` snapshot on `/status`, `orders[]` with all four `block_reason` values, the pagination envelope on list endpoints, `trade_date`/201 on `POST /trades`, and a single 422 `detail[]` parser.

2. **Grid view on the plugin framework**
   - The ETF Grid page fills in the blank plugin view shipped by [v0.1.2](v0.1.2-plugin-framework.md) (`src/plugins/etf-grid/`): API client, types, and page components live inside the plugin directory; the shell is untouched.
   - Chat remains the default view; the existing `thread_id`/`CopilotKit` behavior is untouched.

3. **Grid status page**
   - Per-symbol status table: holdings (shares, avg cost, realized P&L), latest close/market value, current level vs. anchor MA60, gate state (`gate_closed`, `gate_percentile`, `block_reason`) — all read from the `signal` snapshot, with an explicit **empty state when `signal` is null** (no signal computed yet) and nullable-field fallbacks.
   - Signal orders render as a **two-sided bracket** mirroring the Runtime's `orders[]` semantics (`core/grid.py` `compute_signal`): a pending buy leg and a pending sell leg are normally both present every day, plus a triggered order (single side) on level-change days. Each leg shows side, limit price, grids, and kind (`triggered` / `pending`) with `note` badges (`cost_protection`, `gate_closed`); a missing leg is explained per `block_reason` (all four values), never silently omitted. Layout reference: `docs/design/v0.2.0-grid-page-mockup.html`.
   - **Refresh data** action (`POST /sync`) with per-source, per-symbol row counts and partial-failure (`errors`) surfacing; **Recompute signals** action (`POST /signals/compute`).

4. **Trade ledger**
   - Full-width filterable trade list (`GET /trades`: symbol, date range) with all amount columns (gross, commission, net), rendered as a table, with **pagination controls** driven by the envelope (`offset`/`limit` requests, `total` for page count).
   - **Record trade** as a modal opened from the ledger header (`POST /trades` with `trade_date`): symbol, date, side, price, quantity, commission rate, note; local preview of gross/commission/net computed from the inputs; explicit confirm step before submission; the created row (201) refreshes the list.

5. **Presentation plumbing**
   - Shared formatting helpers (money/percent/date display from string inputs), loading and error states for every async surface.
   - Empty states (no trades, `signal: null`, Runtime unreachable).
   - Inline 422 rendering via the single `detail[]` shape (`msg` per item), in the record-trade modal and anywhere else validation can fail.
   - All copy keyed in `src/plugins/etf-grid/locales/en.json` (`useTranslation("etf-grid")`), replacing the v0.1.3 placeholder strings.

6. **Docs & versioning**
   - Update `docs/frontend-architecture.md` (new views, API client layer).
   - Update `AGENTS.md` §3.2 milestone status and §3.3 out-of-scope items that this milestone absorbs.
   - Bump `package.json` version to `0.2.0`.

### 3.2 Out of Scope

- **In-chat custom tool cards** for the four grid tools — moved to [v0.2.1](v0.2.1-etf-grid-chat-tool-cards.md).
- **Signal history section on the page** — dropped by owner decision during layout review; historical signals remain available via the chat tools (v0.2.1) and `GET /signals` if ever needed.
- **HITL confirmation UX in chat** for `record_grid_trade` — deferred until the Runtime adopts Agno `requires_confirmation` (shared HITL path, Runtime ADR 0003 / architecture §6).
- **Proactive signal notifications / updates stream** — belongs to a later automation milestone (Runtime ADR 0003).
- **A router library**, deep-linking, and browser-history integration — deferred until more pages force it.
- **Thread list / management** UI — a separate milestone.
- **Per-Slave visibility and custom AG-UI events** — Runtime ADR 0004 phase 2+.
- **Authentication** — single-user local deployment (Runtime ADR 0005).
- **Charts / visualizations** (price with grid levels, equity curve) — candidate for a follow-up milestone once the base page proves out.
- **Non-English locales for the new copy** — the grid page ships English keys only, per the v0.1.3 convention; zh-CN is a later data-only follow-up.
- **Tests** — still manual verification per milestone walkthrough; the test framework lands in a later milestone.

## 4. Success Criteria

- [ ] The Grid view renders live status for every configured ETF symbol from `GET /status`, with holdings, latest signal orders, and gate state all visible; a symbol with `signal: null` renders an explicit empty state instead of blanks or a crash.
- [ ] **Refresh data** triggers a sync and reports per-source, per-symbol results; a partial failure (e.g. one source down) is surfaced as a warning, not a page crash.
- [ ] The trade ledger shows all amount columns (gross, commission, net), filters by symbol and date range, and paginates correctly (`total` from the envelope matches the page count).
- [ ] A trade recorded through the ledger form (with preview + confirm) appears in the trade list after refresh, and the Runtime echoes matching gross/commission/net.
- [ ] Invalid trade input — both pydantic rejections (e.g. negative price) and domain rejections — shows the Runtime's 422 `detail[]` messages inline through one rendering path; no silent failures.
- [ ] Switching between Chat and Grid views does not reset the chat thread.
- [ ] No hardcoded UI copy: searching `src/` for CJK characters still finds zero user-facing strings, and all new grid copy resolves from the `etf-grid` namespace.
- [ ] `npm run lint` and `npm run typecheck` pass.
- [ ] The app still builds to static files and works served from `dist/`, configured solely via `VITE_AGENT_ENDPOINT`.
