## 2. Context

The Runtime already schedules deterministic HTTP calls through Agno AgentOS.
Its v0.6.4 milestone freezes four read endpoints and their authorization
behavior; the Client needs no new backend or extension-specific API.

The existing sidebar already contains a disabled **Scheduled tasks** entry in
`src/nav.ts`. This milestone activates that entry for ordinary users and adds
the same read-only page to the management-only administrator surface. The
implementation remains core platform UI, not an ETF Grid extension: schedules
are a Runtime capability and ETF Grid is only their first consumer.

The visibility rules are product requirements, not optional client filters:

| Caller | Public system task (`user_id: null`) | Own personal task | Another user's personal task |
|--------|--------------------------------------|-------------------|------------------------------|
| Ordinary user with `schedules:read` | Not returned; direct reads return 404 | Visible | Not returned; direct reads return 404 |
| Administrator with `agent_os:admin` | Visible | Visible | Visible |

The Runtime remains the authorization boundary. The browser must not send an
owner, `user_id`, or “all users” query parameter, and hiding a row in React is
never a substitute for Runtime scoping. “Public” means unowned and
deployment-wide; it does **not** mean readable by ordinary users.

The page is deliberately read-only. Although Agno also exposes write routes,
this milestone adds no create, edit, delete, enable, disable, or trigger
controls and issues only the four GET requests below.

## 3. API and Presentation Contract

### 3.1 Runtime endpoints

| Method | Path | Client use |
|--------|------|------------|
| GET | `/schedules` | Paginated schedule list, with optional `enabled` filter |
| GET | `/schedules/{schedule_id}` | Fresh selected-schedule detail |
| GET | `/schedules/{schedule_id}/runs` | Paginated run history for the selected schedule |
| GET | `/schedules/{schedule_id}/runs/{run_id}` | Expanded execution-attempt detail |

Both list endpoints use Agno's `{data, meta}` envelope. `meta` contains `page`,
`limit`, `total_pages`, and `total_count`. The schedule list uses a fixed client
page size of 20; run history uses 10. Omit `enabled` for the unfiltered list and
send `enabled=true|false` only for the corresponding filter. Page numbers start
at 1. An empty result is a successful response, including `total_pages: 0`.

Add `src/scheduled-tasks-api.ts` on top of `runtimeRequest`, with strict
`Schedule`, `ScheduleRun`, and pagination types matching Agno 3.1.2. Include the
full native response shapes rather than a write-model or a derived API schema.
Encode path ids and accept `AbortSignal` for every request.

Important presentation mappings:

- `user_id === null` → **System** owner/category, visible only in admin mode;
  otherwise → **Personal**. Do not expect a derived `type` field from Runtime.
- `enabled` → Enabled or Disabled state. `disabled_reason` is shown when set.
- `cron_expr`, `timezone`, `method`, and `endpoint` remain raw values; no cron
  parser or humanization dependency is introduced.
- `next_run_at`, `triggered_at`, `completed_at`, `created_at`, and `updated_at`
  are nullable Unix timestamps in **seconds**. Convert to milliseconds before
  constructing a `Date`; render null as an em dash.
- Format schedule timestamps with `Intl.DateTimeFormat` and the schedule's
  `timezone`, and label that timezone. Run timestamps use the browser locale
  and explicitly labelled local timezone. Duration is derived only when both
  trigger and completion timestamps exist.
- Known run statuses such as `success` and `failed` receive familiar badge
  treatment; unknown statuses remain readable verbatim instead of breaking a
  narrow union or rendering blank.
- `status_code`, `attempt`, linked `run_id`/`session_id`, `error`, `input`,
  `output`, and `requirements` are optional detail content. Missing output is
  “Not recorded”, not a successful empty result. JSON values use a readable,
  wrapping `<pre>` presentation.

### 3.2 Page structure and interaction

Use one shared presentational `ScheduledTasksPage` in
`src/pages/scheduled-tasks-page.tsx`, parameterized by `mode: "user" | "admin"`.
The shared `AppShell` remains responsible for navigation and the user area.

1. **Header and list**
   - Title **Scheduled tasks**, a short read-only description, a Read-only
     badge, and a manual Refresh action.
   - A three-state status filter: All, Enabled, Disabled. No owner filter,
     search, auto-refresh, or dashboard metrics in this milestone.
   - Table columns: Task, Schedule, Next run, State. Admin mode adds Owner.
     Do not add a “last run” column: the list response has no such field and
     the page must not fan out one run-list request per row.
   - Task shows `name` and optional `description`; Schedule shows raw cron and
     timezone. Selecting a task opens its detail drawer.
   - Previous/next pagination is driven by response `meta`. Display zero counts
     honestly and disable both controls for an empty result.

2. **Schedule detail drawer**
   - Reuse the vendored shadcn `Sheet`; it becomes full-width on small screens.
     No router or deep link is introduced.
   - Fetch schedule detail and run-history page 1 when selection changes. Show
     independent loading/error states so a run-history failure does not erase
     valid schedule configuration.
   - Overview fields: owner/category, enabled state and disabled reason,
     description, cron/timezone, next run, method/endpoint, timeout, retry
     count/delay, payload, provenance when present, and created/updated times.
   - Run history lists attempt, status, triggered time, duration, and HTTP
     status code, with its own previous/next pagination and empty state.
   - Expanding one run fetches its detail endpoint and reveals timing, error,
     linked ids, input/output, and requirements. Collapsing or changing run
     page aborts/invalidates obsolete detail requests.

3. **State and request discipline**
   - Changing the enabled filter resets to page 1 and closes the drawer;
     changing schedule page also closes it. Selecting another schedule resets
     run page and expanded run state.
   - Refresh reloads the current list page and, when open, the selected detail
     and current run page. Preserve the current filter and pagination.
   - Abort list, detail, run-list, and run-detail requests on superseding state
     changes or unmount; ignore stale completions.
   - A 403 shows a localized access-denied state without retrying
     automatically. A 404 for a selected schedule/run shows “not found or no
     longer accessible”, closes invalid detail state, and offers list refresh.
     A 401 continues through the shared re-authentication path.
   - Provide loading skeletons, empty list, no-description, no-next-run,
     no-runs, request-error, and retry states. Manual refresh is the only
     polling-like behavior; there are no notifications or live updates.

### 3.3 Role-specific navigation

- **Ordinary users**: activate `primaryNav`'s existing `scheduled-tasks` item,
  remove its Soon badge, and add `"scheduled-tasks"` to core `ViewId`
  handling. Selecting it renders the shared page in user mode. Chat remains
  mounted but hidden, exactly as for extension views, so returning to a
  conversation preserves its state.
- **Administrators**: add local `overview | scheduled-tasks` view state to the
  existing admin surface and render Management and Scheduled tasks sidebar
  entries with real active states. The scheduled-task page renders in admin
  mode inside `AppShell mode="admin"`.
- Preserve the hard role boundary: admin mode still mounts no chat,
  CopilotKit provider, thread agent, extension views, or `/agui` requests.
  Client role claims choose presentation only; they never alter request scope.

## 4. Scope

### 4.1 In Scope

1. Typed Agno schedule and run-read API wrappers using the shared Runtime HTTP
   and Bearer-token layer.
2. The shared read-only schedule list, detail drawer, run history, and expanded
   run detail described above.
3. Ordinary-user navigation and administrator navigation to the page, without a
   router or state-management dependency.
4. Pagination, enabled filtering, manual refresh, cancellation, role-aware
   ownership display, timestamp/JSON formatting, and all async states.
5. English `common` namespace copy for every new label and message.
6. Documentation, version, and real-Runtime browser verification.

### 4.2 Out of Scope

- Any schedule write operation or button: create, update, delete, enable,
  disable, and manual trigger.
- Runtime, Agno, Logto, SchedulerTools, agent-tool, notification, or scheduler
  execution changes.
- Owner/search filters, client-side cross-user queries, cron editing or
  humanization, charts, dashboard cards, auto-refresh, and proactive updates.
- Task creation wizards, natural-language schedule management, HITL, domain
  result interpretation, or ETF Grid-specific run cards.
- Router/deep links, a new test framework, new runtime dependencies, and
  non-English locale additions.

## 5. Success Criteria

- [ ] An ordinary user can open Scheduled tasks and sees exactly the personal
  schedules returned by Runtime; public system tasks and other users' tasks
  never appear, and no ownership override is sent.
- [ ] An administrator sees public system schedules and personal schedules
  from multiple users, with an accurate Owner column and System/Personal
  labels derived only from `user_id`.
- [ ] Enabled filtering and schedule/run pagination use Agno's query and
  `{data, meta}` contract correctly, including empty results and zero pages.
- [ ] Selecting a schedule shows its native configuration and run history;
  expanding a run uses the run-detail GET and correctly renders success,
  failure, retries/attempts, null fields, errors, and available JSON payloads.
- [ ] Unix-second timestamps and schedule/local timezones are displayed
  correctly; raw cron expressions remain visible.
- [ ] Loading, empty, error, 403, and stale/404 detail states are understandable;
  obsolete requests cannot overwrite a newer selection or filter.
- [ ] The UI exposes no schedule write action and browser network inspection
  shows only the four documented GET routes for this feature.
- [ ] Switching between Chat and Scheduled tasks preserves the current chat;
  admin mode continues to make zero AG-UI requests and mounts no chat surface.
- [ ] All new copy resolves through the `common` i18n namespace, and the layout
  remains usable with the sidebar collapsed and on a narrow viewport.
- [ ] `npm run lint`, `npm run typecheck`, and `npm run build` pass.

## 8. Manual Verification (owner walkthrough)

Prerequisites:

1. Runtime v0.6.4 is running with user isolation and real Logto JWTs. Fixtures
   include the public `etf_grid_daily_sync`, Alice-owned and Bob-owned personal
   schedules, disabled schedules, successful/failed runs, and enough rows to
   exercise pagination.
2. Logto provides an administrator, ordinary users Alice and Bob, and an
   authenticated test caller without `schedules:read` for the 403 check.
3. Start this app with `npm run dev` on port 3000.

Walkthrough:

1. Sign in as Alice. Open Scheduled tasks; verify only Alice's personal tasks
   appear, the system ETF task and Bob's tasks do not, and request query strings
   contain no owner override. Exercise All/Enabled/Disabled and list pagination.
2. Open a task and verify cron, timezone, next run, endpoint, timeout/retry,
   ownership, payload, and nullable fields. Page through runs and expand both a
   success and a failed attempt; check timestamps, duration, HTTP status,
   attempt, error, and optional JSON. Open a task with no runs.
3. Switch to Chat, send or inspect a conversation, return to Scheduled tasks,
   and then go back to Chat; confirm the conversation was not reset. Refresh
   the task page and confirm filter/page/selection behavior matches Section 3.
4. Sign in as Bob with an empty personal-task fixture. Verify the empty list is
   successful rather than an error, and that Alice's tasks remain invisible.
5. Sign in as admin. Verify Management and Scheduled tasks are the only admin
   navigation entries; the list includes the public system task plus Alice's
   and Bob's personal tasks with correct owners. Inspect a system task and
   another user's run history. DevTools Network shows zero `/agui` requests.
6. Using the no-scope test caller, verify the page's 403 state. Simulate a
   deleted/inaccessible selected schedule or run and verify the localized 404
   recovery. Stop or block Runtime temporarily to verify request error/retry,
   then restore it.
7. Repeat list and drawer checks at a narrow viewport and with the sidebar
   collapsed. Confirm there are no write controls and all feature network
   traffic is GET-only.
8. Run `npm run lint`, `npm run typecheck`, and `npm run build`.
